## Task Reference

## Specification Summary

* `database/postgres/pg_hba.conf` admits application connections only over `hostssl` with `clientcert=verify-full`.
* A certificate generator creates a CA, a PostgreSQL server certificate, and a client certificate into a gitignored directory.
* `docker-compose.yml` mounts the certificates into the postgres and middleware services and sets `ssl=on` on the server.
* `middleware/database.py` defaults `DB_SSLMODE` to `verify-full` when unset, and reads the root CA and client certificate and key from the environment.
* Tests may lower the mode only by setting `DB_SSLMODE` explicitly.

## Implementation Notes

### Files changed

* `database/certs/generate-certs.sh` (new). Generates the CA, server, and client certificates into `database/certs/out/`. Runs under Git for Windows bash, which provides OpenSSL 1.1.1q at `C:\Program Files\Git\usr\bin\openssl.exe`. The PowerShell route was not used because the bash route reuses the Gateway script.
* `database/certs/.gitignore` (new). Ignores `out/`. The root `.gitignore` is unchanged.
* `database/certs/postgres-entrypoint.sh` (new). Copies the server key, server certificate, and CA into `/var/lib/postgresql/tls` with postgres ownership and mode 0600 for the key, then runs the official entrypoint.
* `database/certs/middleware-entrypoint.sh` (new). Copies the client key into `/tmp/biosync-db-tls/client.key` with mode 0600 before the application starts.
* `database/postgres/pg_hba.conf` (new file). The file did not exist when this task started, although the task brief listed it as migrated. It contains the `local` trust row and two `hostssl ... scram-sha-256 clientcert=verify-full` rows. It has no plaintext `host` row.
* `docker-compose.yml`. The postgres service runs the wrapper, sets `ssl=on`, the three certificate paths, and `hba_file`, and mounts the server files and `pg_hba.conf`. The middleware service runs its wrapper, fixes `DB_SSLMODE: verify-full`, sets the root CA, client certificate, and key paths, and mounts the client files. The `127.0.0.1:5432:5432` publish and the service names are unchanged. `ca.key` is not mounted anywhere.
* `middleware/database.py`. `DB_SSLMODE` defaults to `verify-full` in every environment when unset or empty. An unknown value raises at import. `sslmode` is always passed to libpq. The previous code omitted it for `disable` and `prefer`, so libpq used its own `prefer` default and an explicit `disable` had no effect.
* `middleware/tests/test_db_ssl_config.py`. The three strict xfails are converted. Three live tests are added. Two unit tests are added for the empty and unknown `DB_SSLMODE` cases. The `prefer` development default test is replaced by a `verify-full` default test.
* `.env.example`. The cert path variables point at `database/certs/out/`. `DB_SSLMODE` changed from `disable` to `verify-full`. The brief limited this file to path variables, so this line is a deliberate exception. A copy of the old file would have turned TLS off again.
* `docs/db-client-cert-tls.md` (new). Migrated from the Gateway document and corrected as described below.
* `SNDEV/scripts/tls-connection-matrix.py` (new). Runs the three-case connection matrix and prints PASS or FAIL per case. The password comes from an environment variable and is never printed.

### Decisions and deviations

* The three xfails in the file were compose enforcement, pg_hba enforcement, and certificate script wiring. The brief described them as default verify-full, pg_hba enforcement, and rejection without a client certificate. The three converted tests cover the file's existing items. The default and rejection checks are separate tests.
* The client certificate CN equals the database role. The Gateway document described `clientcert=verify-full` as chain verification only. PostgreSQL's `verify-full` also requires the CN to match the user name, and chain-only verification is `verify-ca`. The corrected rule is in `docs/db-client-cert-tls.md`.
* The Gateway document copied `pg_hba.conf` into PGDATA. This change uses `hba_file` with a read-only mount instead, so the file on the host is the one in effect.
* Bind mounts from Windows show every file with mode bits that PostgreSQL and libpq reject. Both wrappers copy the key into a private location with mode 0600 for that reason.
* The first generator draft added CA extensions with `-addext`. Those duplicated `basicConstraints`, which the host default `openssl.cnf` already writes, and the duplicate made the CA fail verification. The current generator writes the CA extensions to `ca.cnf` and sets `subjectKeyIdentifier` and `authorityKeyIdentifier`. Leaf certificates use explicit extension files.
* Git for Windows bash cannot pass POSIX absolute paths to its MinGW openssl. The generator runs inside `out/` and uses relative file names. It also sets `MSYS_NO_PATHCONV` so that `/C=US/...` subject strings reach openssl unchanged.
* A throwaway client certificate with CN `someone-else` was issued from the same CA in a temp directory. The temp directory was removed afterwards. Nothing was written to the repository.
* No `docker compose up` was run. The compose project name matches the running 5432 container, and `up` would recreate it. The 5432 container still runs with `ssl=off` and its original `pg_hba.conf`. It needs recreation before it can enforce this configuration, and that recreation is outside this task.
* The middleware image was not run with the new wrapper. The postgres wrapper and the TLS server behavior were exercised on the scratch server. The middleware wrapper is validated by `docker compose config` only. See Open items.
