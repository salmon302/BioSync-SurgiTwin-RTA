# SOUP and OTS Inventory

Software of unknown provenance (SOUP) and off-the-shelf (OTS) items used by the SurgiTwin-RTA system. This inventory responds to DEVELOPMENT_PLAN.md Section 6.2 VAL-012, which asks for an inventory, version pinning, evaluation, and an anomaly response for each item. It is created in Phase 2 task 2.2 and extended in each later phase. The first record is `SNDEV/docs/impl-2026-10-14-phase2-kickoff.md`.

Pin status values:

* pinned: an exact version or commit is recorded in a tracked file.
* precondition: the item is not yet selected or installed. Its phase task names the precondition.
* license confirm: the license is not verified against the pinned release. DEVELOPMENT_PLAN.md Section 2 marks it "(confirm)".
* pin gap: the item is used, but no exact pin exists in a tracked file.

Notes on the Pulse row. The engine runs inside a dedicated worker process per engine instance (`middleware/engine/pulse.py`). A native crash or a hung step ends that worker only. The parent marks the simulation ERROR, releases the worker, and raises an error to the caller. The Pulse C++ core is single-threaded per patient, so the worker model is also the scheduling unit.

## Anomaly response policy

Advisory monitoring: each owner of an item reviews the upstream release notes and security advisories at every phase gate, and again when a pin changes. A finding that affects a pinned item is recorded in an implementation log under `SNDEV/docs/` with the item name, the observed symptom, the affected requirement, the workaround, and the decision (accept, pin back, or upgrade). Vulnerability details stay under embargo and are not written into logs or commit messages.

Upgrade policy: no floating versions are used. An upgrade is an intentional edit to the tracked pin file, with an updated row in this inventory and a new evaluation record. Pins are not raised in bulk. A pin change is made only when a defect or advisory affects a requirement, or when a phase task needs the new release.

Re-verification trigger on version change: any change to a pin in this inventory triggers a re-run of the IQ and OQ suites named in the VTM row for each requirement that uses the item, and of the PQ run that measures it where one exists. The implementation log for the change cites the captured output under `SNDEV/logs/`. The Pulse binding change additionally re-runs IQ-4, OQ-16, and the fail-closed OQ on the rebuilt image.
